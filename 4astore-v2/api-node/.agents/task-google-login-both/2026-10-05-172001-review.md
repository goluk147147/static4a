# Google Sign-In end-to-end on web and mobile, Facebook/Instagram hidden

Adds a public `POST /api/users/social-login` endpoint that verifies Google ID tokens against both the web and Android OAuth client IDs and returns the exact `{ user, token, refreshToken? }` session shape as `/login` by reusing `issueTokens()`. The web Login page wires real Google Identity Services via a runtime `<script>` tag (no new web dependency); the mobile Login screen uses `expo-auth-session` (the SDK-54 trio was confirmed build-safe via an Android prebuild). Facebook and Instagram buttons are hidden behind a `SOCIAL_FB_IG_ENABLED = false` flag on both platforms, with their plumbing retained for later re-enable. Server-side upsert is by email with a non-colliding `g`-prefixed mobile placeholder and a unique username, retrying on unique-constraint races so it never crashes.

Watch for: the mobile cleartext config moved from a dropped `android.usesCleartextTraffic` field into the existing `withCleartext` plugin — behavior is preserved but the two files now derive the http:// test from different expressions (confirmed, non-blocking). The social-login endpoint's error branches and P2002 retry are verified by review + clean tsc only, since api-node has no test runner (confirmed, non-blocking).

**Verdict**: APPROVED

## High-level view

The server is the single trust anchor: it verifies the Google ID token with `google-auth-library` against an audience array holding both client IDs, so one endpoint serves both clients, and it rejects a non-google provider before touching the token. The session is minted by the same `issueTokens()` used by `/login`, so downstream auth, refresh, and `isMobileClient` handling are identical — no parallel session path was introduced.

New-user creation derives a username from the email local-part and a mobile placeholder of `g` + the Google `sub` digits. The `g` prefix deliberately cannot satisfy the real-mobile regex `/^[6-9]\d{9}$/`, so a Google account can never collide with or impersonate a phone-registered user, and a bounded retry re-suffixes both fields on a P2002 race rather than crashing.

The web client adds zero dependencies — Google Identity Services loads from a runtime script tag, gated so an empty `VITE_GOOGLE_CLIENT_ID` never loads the script and falls back to the existing setup-pending toast. The credential callback reuses `setAccessToken` + `setUser`, the same setters as `login()`.

The mobile client ships `expo-auth-session`/`expo-web-browser`/`expo-crypto` pinned to their SDK-54 versions, and the Android prebuild build-safety gate was re-run here and passed, so the APK build is not at risk. The success path calls a new `socialLogin()` store action that mirrors `login()` exactly, then runs the unchanged `done()` so push registration and routing are preserved.

Facebook and Instagram are hidden the same way on both platforms — a literal `false` flag guarding the JSX while keeping the buttons' plumbing — so re-enabling later is a one-line flip. The only collateral change is the mobile cleartext config relocating into the `withCleartext` plugin because its old manifest field was dropped from `@expo/config-types` in SDK 54.

### One endpoint, two audiences, same session as /login

The endpoint hands both client IDs to `verifyIdToken({ audience: [GOOGLE_WEB_CLIENT_ID, GOOGLE_ANDROID_CLIENT_ID] })`, so a token minted for either the web GIS flow or the Android app validates through the same path. A single stateless `OAuth2Client` is created at module load. Validation ordering is deliberate: an explicitly non-google `provider` is rejected with 400 before any token work, a missing/empty `idToken` returns 422 via the zod schema, and anything that fails verification — bad signature, wrong audience, or a payload missing `email_verified === true` or `email` — collapses to a single 401 "Invalid Google token" that doesn't leak which check failed.

The session is minted by the existing `issueTokens(res, user, isMobileClient(req) ? 'mobile-app' : undefined)` and returned as `{ user: safeUser(user), token, ...(mobile ? { refreshToken } : {}) }` — byte-for-byte the `/login` contract, including that `refreshToken` appears only for `X-Client: mobile`. No separate token logic was introduced, so refresh, cookie lifetime, and claims stay in one place.

### Email upsert with a collision-proof placeholder identity

```
verify token ──> findFirst(email OR recovery_email)
                      │
            found ────┴──── not found
              │                 │
       update last_login   createGoogleUser(payload)
                                 │
                   username = emailLocalPart (a-z0-9, padded to ≥3)
                   mobile   = ('g' + sub.digits).slice(0,15)
                                 │
                   create ──P2002──> re-suffix username+mobile, retry (≤5)
```

The placeholder mobile is prefixed `g`, which cannot match the register regex `/^[6-9]\d{9}$/`, so a Google-created account can never occupy or collide with a real phone number's namespace — a genuine security-relevant choice, since mobile is a unique login identifier here. On a unique-constraint race the loop re-suffixes both `username` and `mobile` up to five times and only rethrows the captured P2002 if every attempt loses, so concurrent first-logins degrade gracefully instead of surfacing a 500. The generated password is a random 24-byte hex run through bcrypt, so the placeholder account has no guessable credential.

### Web Google via GIS with no new dependency

Google Identity Services is injected as a one-time `<script async defer>` inside a `useEffect` that returns early when `VITE_GOOGLE_CLIENT_ID` is empty, so an unconfigured build never loads Google code and the button keeps its bilingual setup-pending toast. A second effect calls `initialize()` once (guarded by a `useRef`) after the script signals ready. The credential callback posts `{ provider:'google', idToken }` through the shared axios `api` and stores the session with `setAccessToken(data.token)` + `useAuth.getState().setUser(data.user)` — the same two setters `login()` uses — then navigates to `next`. No `@react-oauth` or other package was added, satisfying the no-new-web-dep constraint.

### Mobile expo-auth-session flow, build-safety confirmed

The build-safety gate is the risky part of this change, and it was re-run independently here: `npx expo prebuild --platform android --clean --no-install` finished with EXIT=0 ("Finished prebuild"), emitting only the pre-existing non-fatal `userInterfaceStyle: Install expo-system-ui` warning. The generated `android/` directory was deleted afterward and `git status` confirms it was never committed. The three new deps are pinned to their SDK-54 managed versions (`expo-auth-session ~7.0.11`, `expo-web-browser ~15.0.11`, `expo-crypto ~15.0.9`) and `expo-web-browser` was added to the `plugins` array as that package requires.

`Google.useAuthRequest` is configured with both client IDs and `responseType: 'id_token'`. The button gates on an empty web client ID (setup-pending toast) and is disabled while busy or while the auth request is still initializing. The response effect reads `params.id_token` with a fallback to `authentication.idToken`, calls the new `socialLogin(idToken)` store action, then runs the unchanged `done(user)` so `registerForPush()` and role-based routing fire exactly as they do after a password login. The effect uses a `cancelled` guard so a unit that unmounts mid-flight won't set state on a dead component.

`socialLogin()` in the mobile store mirrors `login()` line-for-line — `api.post` (which already stamps `X-Client: mobile`), `setAccessToken`, conditional `saveRefreshToken`, `normalizeUser`, `set({ user })`, return user — so the mobile session is populated identically whether the user signs in with a password or Google.

### Facebook/Instagram hidden identically on both platforms

Both Login screens gate the FB/IG buttons behind `const SOCIAL_FB_IG_ENABLED = false`, rendering them only inside a `{SOCIAL_FB_IG_ENABLED && (…)}` block so the literal-false flag keeps them out of the DOM/tree while the button markup and handlers remain in place for a later one-line re-enable. The "or continue with / या इसके साथ जारी रखें" divider and the Google button's bilingual label and styling are untouched, matching the requirement to change only visibility.

### Cleartext config relocation (collateral)

`app.config.ts` dropped its top-level `android.usesCleartextTraffic` field because `@expo/config-types` removed it in SDK 54 — leaving it caused a baseline TS2353 that would block the typecheck gate. Its runtime effect was folded into the existing `withCleartext` config-plugin, which now triggers on `STORE4A_ALLOW_HTTP=1` OR an `http://` API base. The plugin reads `process.env.STORE4A_API_BASE || ''` directly while `app.config.ts` derives `API_BASE` with an `https://` default; the two expressions produce the same cleartext decision (the default can never be http://, an explicit http:// value trips both), so Android cleartext behavior is unchanged. The divergent expressions are the only reason to flag this — a shared helper would remove the drift risk.

### Verification re-run

All four gates were re-executed in the worktree: api-node `npm run build` (tsc) EXIT=0 after regenerating the real Prisma client, web `npm run build` EXIT=0, mobile `npm run typecheck` EXIT=0, mobile `npm test` 27/27 pass, and the Android prebuild build-safety gate EXIT=0. Existing login/register/forgot-password, tracking, rider, and payments routes are untouched by the diff — the API change is purely additive (a new route plus two helpers), and the client changes are confined to the Login screens, the two config/store files, and the cleartext plugin.

### Not tested

api-node has no unit-test runner, so the social-login 401/400/422 branches and the P2002 retry loop are confirmed by code reading and a clean tsc build, not by an executed request. The Google verify path itself requires outbound HTTPS to Google's cert endpoint at runtime (noted in context.json) and was not exercised live.
