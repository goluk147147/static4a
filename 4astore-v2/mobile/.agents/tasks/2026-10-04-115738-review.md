# Local-first address flow, cached-first read screens, and optimistic staff status change

The branch replaces three network-blocked flows that were freezing the app on a slow connection. The checkout address flow now reads from AsyncStorage instantly on mount, saves optimistically with no network-blocked Save button, and does zero `/addresses` POST on Proceed. My Orders and the CMS Help/Legal pages render last-cached content immediately, show a Shimmer skeleton only on true first load, and fall back to cache (or a friendly empty state) on error instead of an endless spinner. The staff order status change applies to the React Query cache immediately and rolls back on failure. The `src/api.ts` 401 path and `src/store/auth.ts` logout/bootstrap were audited (comment-only changes) and confirmed bounded and local-first. No new dependency, no server/response-shape change, and tracking/rider files are untouched.

Watch for: nothing blocking. The reconcile-by-match heuristic for optimistic address rows (confirmed) and the Proceed button's `disabled={loadingAddr}` gate (confirmed) are the two behaviors worth a glance, both acceptable as designed.

**Verdict**: APPROVED

## High-level view

The address store (`src/store/addresses.ts`) is a clean, dependency-free port of the `persistCache.ts` pattern: per-user versioned key, a pending queue for offline writes, negative temp ids for optimistic rows, and try/catch around every storage and network call. Checkout serves local addresses before any network await and fires sync + flush in the background behind a `cancelled` guard. Create payloads correctly send `id: undefined`, never a temp id.

The two read screens follow one shape — hydrate a `cached` state from a mobile/slug-scoped cache, persist fresh query data, render `fresh ?? cached ?? []`, show the skeleton only when loading with no data, and keep cached content visible on error. Neither screen can land on a bare infinite spinner.

The staff status change is optimistic against both `['order', id]` and `['all-orders']` with a snapshot/rollback and the existing error toast; the button spinner no longer spans the network call. The api.ts and auth.ts edits are documentation of already-correct behavior — the 401 recovery is single-shot (guarded by `_retried`), single-flight (shared `refreshing` promise), and resolves to a thrown ApiError on refresh failure, while logout clears the local session regardless of network outcome and bootstrap releases the splash in `finally`.

Security posture is intact: Bearer header, SecureStore refresh token, and `X-Client: mobile` are all unchanged, and no AbortController or session-expiry hook was invented.

### Local-first address store and checkout rewire

`src/store/addresses.ts` exports exactly the FEAT-001 surface — `loadLocal`, `saveLocal`, `upsertLocal`, `syncFromServer`, `queuePending`, `flushPending` — plus the `PendingPayload` interface, all using only AsyncStorage and the existing `api`. Keys are per-user and versioned (`4astore:addresses:v1:<userId>`, `...pending:v1:<userId>`). Every storage and network call is wrapped so a corrupt blob or offline write degrades to `[]`/`null` rather than throwing into the UI.

Checkout's mount effect serves `loadLocal(userId)` before any network await, fills the default (or first) address or opens the editor on an empty list, then fires `syncFromServer` and `flushPending` in the background behind a `cancelled` guard so a late resolve after unmount can't set state. `saveFromEditor` keeps all validation unchanged, writes the optimistic row via `upsertLocal`, closes the editor and toasts synchronously, and fires the POST in the background — `savingAddr` is held only across the synchronous local write. The create/update split is correct: a positive `selectedId` goes up as an update, otherwise `id: undefined` with action `create`, so a negative temp id never reaches the server. `proceed()` builds the customer and opens the payment sheet with no `/addresses` POST.

The reconcile path (both in `flushPending` and inline after a background save) matches the server row to an optimistic temp row by `phone+house_no+pincode`, falling back to the oldest temp. This is a heuristic — two offline saves with identical phone/house/pincode could swap, but the authoritative `syncFromServer` list overwrites local on the next mount, so any mismatch is transient.

### Cached-first My Orders and CMS pages

Both screens use the same shape added to `persistCache.ts`: `loadOrdersCache/saveOrdersCache` keyed by mobile and `loadPageCache/savePageCache` keyed by slug, each try/catch and deliberately kept out of `PERSIST_KEYS` so per-user/per-page data isn't bundled into the storefront snapshot. Orders renders `q.data ?? cached ?? []`; the `OrdersSkeleton` (three Card-shaped Shimmer rows) shows only on `q.isLoading && !orders.length`, error-with-cache keeps the rows plus a retry hint, error-without-data shows the retry line, and the genuinely-empty case keeps the EmptyState. The 7s `useAllOrders` poll is untouched.

The CMS page seeds `cached` from `loadPageCache(slug)`, renders `data ?? cached`, shows `PageSkeleton` only on first load, and falls back to the "Page not found" EmptyState on error with no cache. The WebView CSP, `originWhitelist`, `baseUrl`, `javaScriptEnabled={false}`, and `onShouldStartLoadWithRequest` interception are all unchanged.

### Optimistic staff status change

`setStatus` in `app/admin/order/[id].tsx` snapshots `['order', id]` and `['all-orders']`, writes the new `order_status` into both caches immediately, then POSTs in the background — invalidating on success, restoring both snapshots and showing the existing `apiError` toast on failure. The old `saving` state and the Button `loading` prop are gone, so the button no longer spins across the network; selected state is shown via `outline={o.order_status !== st}`. The comment documents that this is the reported "staff delete loader" surface and that no DELETE endpoint exists in the mobile app.

### 401/refresh and auth audit (comment-only)

`src/api.ts` and `src/store/auth.ts` changed only in comments. The 401 branch is reachable once per request (`_retried` guard), shares a single-flight `refreshing` promise across concurrent 401s, excludes the auth endpoints from retry, and falls through to a thrown `ApiError` when refresh returns null — no loop, no unresolved promise. `refreshSession` clears the refresh token only on 401/404, keeping it across transient network errors. Bearer header, SecureStore storage, and `X-Client: mobile` are present on both the main request and the refresh. Logout clears the local session even when `unregisterPush`/`/users/logout` fail, and `bootstrap` sets `ready` in `finally` so a failed refresh releases the splash.
