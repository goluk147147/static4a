# Native Google Sign-In for 4A Store v2 mobile

The mobile app's Google button was wired through `expo-auth-session`'s custom-URI web flow, which current Google policy blocks on standalone Android builds (`Error 400: invalid_request`). This change replaces that flow with the native `@react-native-google-signin/google-signin` library (pinned `16.1.5`), registers its Expo config plugin, bumps the Android `versionCode` to 21, and rewrites the login button handler to run the native sign-in sheet and hand the WEB-client `idToken` to the existing `socialLogin()` store action unchanged. The server `/social-login` endpoint, the web storefront GIS login, and `src/store/auth.ts` are deliberately untouched; the remaining work is owner-side Google Cloud / rebuild config captured in the plan.

Watch for: nothing blocking. The migration is code-complete and verified green; the end-to-end success path depends entirely on owner-side console/build steps (Play App Signing SHA-1, re-downloaded `google-services.json` with a populated `oauth_client`, versionCode-21 binary) that cannot be exercised in-agent — **possible** failure point if those are skipped at ship time.

**Verdict**: APPROVED

## High-level view

The design swaps one `idToken` producer for another without disturbing the consumer contract. The native library mints a token for the WEB OAuth client id, which the server's `/social-login` audience list already accepts, so the entire server and session path stays byte-for-byte identical and the blast radius is confined to `login.tsx` plus config wiring.

The gating strategy is preserved exactly: an empty `GOOGLE_WEB_CLIENT_ID` keeps the button on its bilingual "setup pending" toast and skips `configure()`, so a build with no provisioned web id is still safe. `SIGN_IN_CANCELLED` is treated as a silent no-op and every other failure routes through `apiError()` to a toast, matching the prior UX.

The API surface change is minimal and config-only: one exact-pinned dependency, one bare plugin string (Firebase variant, no `iosUrlScheme`), the `versionCode` bump, and comment updates on the two client-id config sites. No new flags, env vars, or endpoints.

The known gap is entirely owner-side and well-documented: the checked-in `google-services.json` has an empty `oauth_client`, the Play App Signing SHA-1 is not yet registered, and a new versionCode-21 binary must ship. Native sign-in will fail with `DEVELOPER_ERROR` until those are done, and none of it is verifiable from the code alone.

### Token producer swap behind an unchanged consumer contract

The migration rests on one fact: both the old and new flows yield an `idToken` whose audience is the WEB client id, and the server already accepts that audience. `api-node/src/routes/users.ts` verifies with `audience: [GOOGLE_WEB_CLIENT_ID, GOOGLE_ANDROID_CLIENT_ID]` (line 236, unchanged on the base), WEB id defaulting to `707085023016-etp7au34rg3cd5eks6cdu0cs0vkj1svn...`. The native library mints for that WEB id, so `socialLogin(idToken)` receives the same value shape and the server/session path is untouched (**confirmed** — server, web Login, and `src/store/auth.ts` are absent from the diff).

```
old: button → expo-auth-session browser → googleResponse effect → id_token → socialLogin
new: button → native signIn sheet       → res.data.idToken       → socialLogin   (same from here)
                                                                        │
                                                            setAccessToken + saveRefreshToken + user
```

### Button handler rewrite and preserved gating

`startGoogle()` is now async and self-contained; the `googleResponse` `useEffect` and its `cancelled` guard are gone. The empty-web-id "setup pending" bilingual toast fallback is kept ahead of any native call, and `configure()` is guarded on the same non-empty web id in a mount effect, so a build with no provisioned id never touches the native layer (**confirmed**). The missing-token branch early-returns through `finally`, `SIGN_IN_CANCELLED` is matched on `e.code` for a silent no-op, and all other errors go through `apiError(e)` to a toast. `SocialBlock`'s `googleDisabled` drops the now-removed `googleReq` reference and uses `busy` alone.

Behavioral edge (**confirmed**, not a defect): when `isSuccessResponse(res)` is false — an in-progress or no-credential response rather than a thrown error — the handler falls through to `finally`, resets `busy`, and shows no toast, consistent with the cancel handling.

### Config wiring: plugin, pin, versionCode

The dependency is pinned exactly to `16.1.5` in both `package.json` and `package-lock.json` (no caret) — **confirmed**, and the resolved peer deps (`expo >=52.0.40`) are satisfied by this project's Expo 54.x. The plugin is added as the bare string `@react-native-google-signin/google-signin` (Firebase variant, no `iosUrlScheme` for the Android-only target), placed among the existing plugins without disturbing the `googleServicesFile` branch. `VERSION_CODE` default moved 20 → 21 with the env override intact. `npx expo config --json` resolves with the plugin listed and `android.versionCode == 21` (**confirmed** by running it). The `GOOGLE_ANDROID_CLIENT_ID` config export is left in place even though `login.tsx` no longer imports it — correct, since the server still uses that id in its audience list.

### Owner-side runtime dependency (not code)

The code change is necessary but not sufficient. The checked-in `google-services.json` has `"oauth_client": []`, the Play App Signing SHA-1 is not yet registered, the web OAuth client needs `https://4astore.com` as an authorized JS origin, and a new versionCode-21 binary must be built and installed — the fix cannot work on the already-installed build. All six items are enumerated accurately in the plan's OWNER GOOGLE CLOUD / REBUILD REQUIREMENTS section and corroborated by FEAT-003's verify-only reading (**confirmed** against the plan; the console/build state itself is **possible** to be incomplete at ship time and is unverifiable in-agent).

### Test coverage

`npm run typecheck` (tsc --noEmit) passes clean and `npm test` reports 27/27 green (**confirmed** by running both). Not tested: the native sign-in path itself — the Google button cannot be exercised in Expo Go or in-agent; it requires a dev/release build on a device with the re-downloaded `google-services.json`. This is an inherent constraint of the native library, not a coverage gap this change could close.
