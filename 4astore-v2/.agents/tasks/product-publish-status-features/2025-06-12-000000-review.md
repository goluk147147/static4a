# Product publish/unpublish status for the admin

Adds a per-product `status` (`draft | published`) so admins can hide a product until its data is filled in, then publish it to the storefront. The column is added at runtime via the repo's ADD-only `ensureProductStatusColumn()` pattern (no prisma migrate) with a `'published'` default so existing live rows stay visible. New products default to `draft`; a server-authoritative guard blocks publishing while name/price/category/image are missing; the public catalog filters to `published` only; and a new staff-gated `GET /api/admin/products` is the only endpoint that lists drafts so the admin UI can see and flip them.

Watch for: (possible) stale base — the branch diverged from an older `main`, so `git diff main` shows the ShortLink OG feature being deleted even though the branch never touched those files; merging without rebasing would silently revert OG. Everything in the actual branch changeset is on-scope.

**Verdict**: APPROVED

## High-level view

The status column follows the established runtime-ensure convention exactly: `ensureProductStatusColumn()` mirrors `ensureProductMaxQtyColumn()` (information_schema guard, 1060/1061 swallow, `$executeRawUnsafe`, no migrate), is wired into the boot block, and is documented on the Prisma model with an index. The `NOT NULL DEFAULT 'published'` choice keeps every existing row live on deploy, and only the admin `add` path defaults new rows to `draft`.

The read-path split is the pivotal design decision and it's handled correctly. Public `GET /products` and `GET /products/:id` filter `status: 'published'`, so drafts never leak to shoppers, while a dedicated `GET /api/admin/products` (staff-gated, `no-store`) returns all rows plus `status`. `status` is deliberately kept out of `PUBLIC_PRODUCT_SELECT`, so the catalog-leak test shape is unchanged and stays green.

The publish guard is server-authoritative: before writing `status: 'published'` on either add or update, `missingPublishFields()` rejects with 422 when name/price>0/category/image are absent. The client mirrors the same check for instant feedback but the server has the final say. On update, `status` is written only when the client sends it, so an ordinary edit leaves the column untouched.

The only thing outside the feature is a stale-base artifact: the branch's merge-base predates the ShortLink OG work that now lives on `main`, so a `main`-based diff misleadingly shows OG deletions. The branch's own commits touch only the 11 publish-status files.

### Runtime status column, no migrate

`ensureProductStatusColumn()` is a line-for-line sibling of `ensureProductMaxQtyColumn()`: an `information_schema.columns` count guard, then `ALTER TABLE products ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'published'` swallowing 1060, then a `statistics`-guarded `CREATE INDEX idx_products_status` swallowing 1061, all via `$executeRawUnsafe` with no prisma migrate (confirmed). It's exported, added to the `dataImport` import list in `server.ts`, and called in the `app.listen` boot block beside `ensureProductMaxQtyColumn()`. The `schema.prisma` model carries the `status String @default("published") @db.VarChar(16)` line and the `@@index([status], map: "idx_products_status")` as documentation only. The `NOT NULL DEFAULT 'published'` means existing rows are visible the instant the column lands — no backfill, no outage window.

### Draft-by-default, publish guard

`const effectiveStatus = action === 'add' ? (p.status ?? 'draft') : p.status;` gives new products a `draft` default while leaving an omitted update status as a no-op (`statusData` is `{}` when `effectiveStatus` is undefined, so the column is untouched on a plain edit). The guard runs before the write:

```ts
if (effectiveStatus === 'published') {
  const missing = missingPublishFields({ name: p.name, price: p.price, category: p.category, image: p.image });
  if (missing.length > 0) return fail(res, 'Publish ke liye ye zaroori hain / Required to publish: ' + missing.join(', '), 422);
}
```

`missingPublishFields` requires a non-empty trimmed name, `price > 0`, non-empty category, non-empty image. Because the `data` object written to `prisma.product.update` overwrites those fields from the same payload the guard inspected, the check and the write can't diverge — a product cannot reach `published` with a blank required field through this endpoint. The row-button helper posts `name/price/mrp/category/image` from the loaded product alongside `status`, so a publish toggle carries the fields the guard needs rather than a bare `{id, status}`.

### Public filter vs admin list

Public reads filter drafts out: `GET /products` adds `where: { status: 'published' }`, and `GET /products/:id` switches `findUnique` to `findFirst({ where: { id, status: 'published' } })` so a draft id falls through to the existing 404. `status` stays out of `PUBLIC_PRODUCT_SELECT` — filtering in `where` doesn't require selecting it, and leaving the projection alone keeps `catalog-leak.test.ts` green (3/3, unedited, verified by running it; `catalogSelect.ts` unchanged vs merge-base).

The admin source of truth is a new route on the generic admin router:

```
public GET /api/products        -> published only, ETag cache (unchanged behaviour)
admin  GET /api/admin/products  -> all rows + status, requireStaff('products'), no-store
```

Routing it on `adminRouter` (mounted last at `/api/admin`) is safe: the earlier specific mounts (`/videos`, `/links`, `/pos`, `/marketing`, `/seo-auto`) don't claim `/products`, so the new handler resolves without collision. `no-store` keeps freshly-flipped status out of any shared cache, which matters because this is the one endpoint that exposes drafts.

### Admin UI wiring

`AdminProducts.tsx` switches its list source from `useProducts()` to the new `useAdminProducts()` (query key `['admin-products']`, `staleTime: 0`, refetch on focus) so drafts appear. The status badge reuses `stock-badge` styling (green Published / gray Draft), the per-row button toggles Publish/Unpublish, and `setStatus` mirrors the server guard client-side before calling the API, surfacing a server 422 via `apiError`. On success it invalidates both `['admin-products']` and `['products']` so the storefront cache refreshes. The empty-state `colSpan` was bumped 10→11 to match the new column.

### Stale base, not bundled changes

`git diff main` shows the ShortLink OG feature (`og_image`/`og_title`, `ensureShortLinkOgColumns`, `shortlinkOg.test.ts`, `ogShare.ts`) being deleted, which would fail the "no unrelated code" check at face value. It isn't: the branch's two commits touch only the publish-status files, and diffing the merge-base (`15ed0da`) against HEAD for those OG paths produces nothing — the branch never changed them. `main` gained the OG work after this branch forked. The practical risk is a merge/rebase hygiene one: land this on current `main` (rebase) so the OG feature isn't reverted by a stale diff.
