# Implementation Plan — Festival Ad Template Library (admin-ads.js)

## Scope and ground rules

All edits are confined to ONE file:
`4astore-v2/web/public/legacy/js/admin-ads.js` (worktree root: `c:\xampp\htdocs\static4a\.worktrees\festival-ad-templates`).

This is a classic vanilla-JS script served verbatim from `web/public/legacy/js/` and loaded by the thin React wrapper `web/src/pages/admin/AdminAds.tsx`. Do NOT move the editor into React, do NOT change architecture, do NOT add dependencies. Storefront/checkout are untouched.

### Design decisions (made here, grounded in the code I read)

1. **Keep the existing template shape and renderer.** Each template is `{ name, emoji, bg:[c1,c2], accent, text }`. The renderer at `adDraw()` reads only `tpl.bg[0]`, `tpl.bg[1]`, `tpl.accent`, `tpl.emoji`, and `tpl.name` (picker card). The `text` key exists in the documented shape but is NOT consumed anywhere today. New templates ADD entries to the `AD_TEMPLATES` object (around line 29); they drop into the picker (`Object.entries(AD_TEMPLATES)` around line 237) and the canvas (`AD_TEMPLATES[e.template]` around line 929) with zero renderer rewrite. This is the lowest-risk way to hit ~50 templates. **Rationale:** picker and canvas are already data-driven off the object, so growing the object is purely additive.

2. **Add a NEW optional `greeting` field to templates for festive copy.** Item 2 (Navratri) and item 4 (content completion) need per-template devotional/festive caption text. Rather than overload the unused `text` field (ambiguous meaning), add an explicit optional `greeting` string to the templates that need it. It is consumed in exactly two safe places: `adSetTemplate()` (to seed the editor's caption when empty) and `adGenerateContent()` (as a festive prefix). Templates without a `greeting` behave exactly as today. **Rationale:** explicit field name, no change to the canvas renderer, backward compatible.

3. **App-download CTA goes in the FOOTER block, not per-template.** The footer renderer (around lines 1347–1360) draws a phone+site line then address lines, anchored to the bottom via `footerTop`/`footerH`. Adding one app line in the footer makes it appear on EVERY template with no per-template work. The footer height math (`footerH`, `footerTop`) must be grown by exactly one app-line height so the new line does not overlap the address lines or push off-canvas. Also add `'Download App'` to `AD_CTAS` so it is selectable as the button text. **Rationale:** item 3 explicitly prefers the footer text block "so every template shows it with no per-template work."

4. **Devanagari rendering reuses the existing font stack.** The renderer defines `const FONT = '"Nirmala UI","Noto Sans Devanagari","Mangal","Segoe UI",Arial,sans-serif';` (around line 981) and all Hindi today (header tagline, footer address) is drawn with `ctx.font = '... ' + FONT; ctx.fillText(...)`. New Hindi text (app line, greetings) MUST use this same `FONT` constant and the same `ctx.fillText` path so it renders with Nirmala UI / Noto Sans Devanagari and does not become tofu/boxes. No new font work is needed.

### Verification reality (discovered during exploration)

- There is **no unit-test framework** for the legacy JS; it lives in `public/` and is copied verbatim by Vite, so `tsc -b` does NOT type-check it.
- Automated checks available:
  - `node --check <file>` — confirms the edited JS still parses (baseline currently passes).
  - `npm run build` (in `web/`) — runs `generate-sitemap.mjs` + `tsc -b` + `vite build`; confirms the React project still compiles and the asset pipeline (which copies `public/legacy/js/admin-ads.js`) succeeds. The `.tsx` wrapper is unchanged, so a green build proves nothing in the app regressed from this change.
  - A one-off Node assertion script (temporary, deleted after) can load the `AD_TEMPLATES`/`AD_CTAS` literals and assert counts, unique kebab-case ids, and required keys. This is the closest thing to a data unit test and is the real verification for the template-count items — NOT a grep.
- Manual visual verification: `npm run dev` in `web/`, open the admin → Ads & Social → Poster, click through templates and confirm palettes differ, Devanagari renders, footer app line shows without overlap, caption includes the Play Store link. Note manual steps in the PR; they are not a substitute for the build passing.

## Notes / assumptions

- Palette authoring is a judgment task; the implementer picks tasteful 2-stop gradients. The only hard constraints: distinct gradients across templates, `accent` legible on the gradient, white text, Navratri days visibly different from each other and devotional in tone.
- `name` strings must stay short enough for the 96px picker card; put the identifying roman+Devanagari after an em dash for Navratri days.
- Prices/MRP/discount remain product-driven — no template or greeting sets price fields.
- If `tcs -b` surfaces an unrelated pre-existing error unrelated to this change, record it in the PR rather than "fixing" out-of-scope code; the ads change itself is isolated to one `public/` JS file that `tsc` does not compile.
