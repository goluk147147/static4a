Build an admin-composed branded email broadcast (title + description + image → emailed to all
real-email customers) for the Node/TS + Prisma(MySQL) + React(Vite) app. Server + web only, NO app

- **Image upload**: `web/src/lib/admin.ts` `uploadBannerImage(dataUri)` → `POST /api/admin/banners/upload` → returns a RELATIVE url `/api/uploads/banners/<name>`. - **UI to mirror**: `web/src/pages/admin/AdminNotify.tsx` (compose form: title/body/image + `uploadBannerImage`, live preview, `sendBroadcast(...)`). `sendBroadcast` lives in `web/src/lib/admin.ts`.
- **Nav/routing**: `web/src/pages/admin/AdminApp.tsx` `ADMIN_TABS` array + `web/src/App.tsx` nested `<Route>`s under `/admin`. Push is `notify` → `<AdminNotify/>`. We add an `email` tab + route the same way.

## Design decisions (made here, grounded)

1. **Backend placement**: put the endpoint + pure helpers in the existing generic `routes/admin.ts` (mirrors sibling POSTs like `/products`, `/banners`), guarded per-route by `requireAuth, requireStaff('ads')`. Chosen over a new router file to match the generic-admin convention and avoid a new mount in `server.ts`.
2. **Pure, testable helpers**: extract `selectEmailRecipients(users, target)` and `renderBroadcastEmail(...)` as pure functions so they unit-test without a DB/SMTP socket (same technique as `emailTemplate.test.ts`).
3. **Unsubscribe**: add a public `GET /api/users/unsubscribe?u=<userId>` that flips ONLY `marketing_opt_out=true` for that user and returns a tiny HTML confirmation. Uses `userId` (no new column, no migration). Footer link `${API_ORIGIN}/users/unsubscribe?u=<id>` per recipient. This is small and safe (exposes nothing, idempotent), so we implement it rather than the "contact support" fallback.
4. **Image absolutization**: server converts a relative `/api/...` or `/...` `imageUrl` to absolute using `SITE_ORIGIN`/`API_ORIGIN`; an already-absolute `http(s)` URL is passed through. Reason: Gmail/Outlook need absolute image URLs; `uploadBannerImage` returns a relative path.
5. **Web UI shape**: add a NEW page `web/src/pages/admin/AdminEmail.tsx` + a new `ADMIN_TABS` entry (`path:'email', key:'ads'`) + a route in `App.tsx`. Chosen over a tab-inside-AdminNotify because AdminNotify is already a two-view (list/compose) component and mixing push+email there muddies it; a sibling page is cleaner and matches how Marketing/Links were added as their own tabs.
6. **No batching**: ~20 users, Brevo 300/day → simple sequential loop with a tiny delay (e.g. 150ms). Count ok/fail from `MailResult`; never throw out of a failed send; on SMTP down return an honest summary (never 500).

## Out of scope / do NOT change
OTP flows, checkout gate, admin-403 scoping, pos-login no-downgrade guard, `renderOtpEmail`/`renderBrandedEmail` and their tests, Prisma migrations (no `migrate`/`db push`). The pre-existing `users.ts:~183 mobile:null` tsc error is an environment artifact — new code must be clean, but do not try to "fix" that pre-existing line.

## Follow-ups / notes for the implementer
- No send-history persistence is included (push has a notifications table; email does not, and the owner only asked to send). If history is wanted later, that's a separate feature.
- The unsubscribe endpoint is intentionally minimal (flips `marketing_opt_out` only). If a token-signed unsubscribe is ever required, that's a later hardening step.
- `MAIL_*` env (Brevo SMTP) is already configured; the feature depends on it. With mail unconfigured, sends report `{ok:false}` and the endpoint returns an honest `sent:0/failed:N` summary rather than erroring.
